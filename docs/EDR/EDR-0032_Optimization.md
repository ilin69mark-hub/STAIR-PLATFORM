# 1. Purpose

Документ фиксирует Advanced Optimization (Phase B, B1) — первый элемент
Engineering Expansion bounded context (BC-002). Цель — «не просто посчитать
марш, а найти лучший»: детерминированный поиск оптимальной конфигурации
(число ступеней, разбивка на марши, шаг комфорта) из допустимого множества,
удовлетворяющего нормативным ограничениям (EDR-0002), по целевой метрике —
итоговая цена, себестоимость или стоимость материала. Solver остаётся
single-shot закрытой формулой; оптимизация — внешний слой, перебирающий
дискретные параметры и вызывающий существующий конвейер как оценщик.

Ключевое решение: **детерминированный исчерпывающий поиск** по дискретной
сетке (число ступеней × число ступеней нижнего марша × шаг комфорта).
Генетические/метаэвристические алгоритмы не используются: инвариант
детерминизма (ADR-0003) требует воспроизводимого результата для одинакового
входа, а пространство поиска ограничено (высота подъёма нормирована
диапазоном высоты ступени 150–200 мм → ≤ десятков значений n).

Состав:

1. **Движок** — `internal/engine/optimization`: универсальный поиск по
   сетке (Candidate/Evaluator/Options/Result), не зависящий от домена.
2. **App-слой** — `stair.Service.Optimize`: вывод границ, оценщик
   (кандидат → конфигурация → конвейер → цель), сборка результата.
3. **Транспорт** — `POST /api/v1/stairs:optimize` (+ проектный вариант
   `POST /api/v1/projects/{id}/optimize`).
4. **Frontend** — кнопка «Оптимизировать» в редакторе, применение
   лучшей конфигурации.

# 3. Model

## 3.1 Параметры поиска

| Параметр | Диапазон | Тип | Примечание |
|---|---|---|---|
| n — число ступеней | `[ceil(H/200), floor(H/150)]` по умолчанию; переопределяется | дискретный | h=H/n должен быть в [150,200] |
| n1 — ступени нижнего марша | `[1, n-1]` для L/U; вырожден для straight/spiral | дискретный | разбивка маршей с площадкой |
| S — шаг комфорта | `[600, 640]` по умолчанию; вырожден для spiral | непрерывный (сетка, шаг 2 мм) | b = S − 2h |

Цель (Target): `price` (FinalPrice), `cost` (ProductionCost), `material`
(Material). По умолчанию — `price`; все цели — минимизация (меньше лучше),
поддерживается `Maximize`.

## 3.2 Движок поиска

`optimization.Search(eval, opt)`: фиксированный порядок обхода
(n → n1 → S), строгая фильтрация по `valid`, сравнение по цели, при
равенстве выигрывает первый встреченный кандидат — детерминизм
(ADR-0003). `Evaluator` — чистая функция без побочных эффектов.

## 3.3 Оценщик (app-слой)

Для кандидата (n, n1, S): `cfg.StepHeight = H/n` (решатель даёт ровно n),
`cfg.LowerStepCount = n1`, `opts.ComfortStep = S`; прогон `Calculate`.
Кандидат допустим, если нет ошибки, `!Validation.Blocking` и есть `Price`.
Значение цели берётся из `Price` (мажорные единицы валюты для ранжирования).

## 3.4 Результат

`OptimizeResult`: `Valid`, `Evaluated`, `Target`, `Objective` (мажорные
единицы), `BestConfig` (H/n, n1, S) и `BestResult` — полный расчёт лучшего
кандидата (повторный детерминированный прогон конвейера).

# 4. Security

- Эндпоинты `stairs:optimize` — под аутентификацией (`authProtected`).
- Проектный вариант — членство + право `project.edit` (как calculate).
- Входы валидируются (422); оптимизация не мутирует данные (stateless).
- Цель ограничена известным набором (иначе 422).
