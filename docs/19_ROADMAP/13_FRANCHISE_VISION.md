# Purpose

Зафиксировать, как платформа должна выглядеть при продаже сети франшиз,
и что мешает сделать это на текущем single-tenant коде. Документ — не план
работ и не обязательство: это цель и разбор разрыва, чтобы решение принимать
осознанно, когда появится первый реальный франшиз.
```

## Решение владельца (2026-09-25)

Продажа сети отложена. Сейчас делается **admin store для текущего одного
store** (см. `REPORTS/` по волнам store-admin). Документ остаётся как
техническая подготовка и как обоснование архитектурных решений, которые
сегодня принимаются (tenant-scoped данные, отсутствие глобальных
настроек, отдельные счётчики и т. п.).

## Что мешает продать как франшизу сегодня

Разбор сделан при изучении (факты, `file:line`):

1. **Публичные флоу прибиты к одному tenant.** Регистрация всегда кладёт
   пользователя в `default` (`internal/application/auth/service.go:167-192`),
   публичные заказы и отзывы — тоже (`internal/transport/http/orders.go:238-272`,
   `testimonials.go:43-64`), каталог материалов и услуг tenant не принимает вовсе
   (`public_materials.go:48-82`, `public_payment_tiers.go:21-44`).
2. **Tenant почти не развит.** `tenants(id, name, slug, created_at)` —
   `migrations/000003_multi_tenant_auth.up.sql:10-18`; нет статуса, плана,
   подписки, домена, бренда, валюты, soft-delete, tenant-CRUD.
3. **Настройки tenant = только security policy** в JSONB
   (`migrations/000012_enterprise.up.sql:4-14`), контента, цен и бренда нет.
4. **Роли только `user` / `admin` глобально**
   (`internal/application/auth/entity.go:14-20`, `:82-98`); нет роли
   «управляющий точкой», «маркетолог», «владелец точки».
5. **Никакой аналитики сайта**: нет pageview/visitor/session/UTM/referrer/device,
   нет воронки; `audit_events` — журнал безопасности с retention 90 дней
   (`migrations/000011_audit_events.up.sql`, `cmd/worker/main.go:124-133`).
6. **Материалы и прайсы — константы в коде** (`internal/engine/manufacturing/material.go`,
   `internal/engine/pricing/pricing.go:61-82`), редактируются только как
   переопределение в теле одного расчёта.

## Целевая модель (как я понимаю продажу)

- **Tenant = франшиза.** Свой контент, прайс, каталог материалов, услуги,
  домен, письма и метрики.
- **Точка (location) внутри тенанта** — если у одной франшизы несколько
  производств/выставочных залов: свои цены/склад/персонал при общих правилах
  платформы.
- **Публикация по домену.** Запрос витрины определяет tenant по host
  (`Host → tenant`), а не по «default». Это ключевое изменение: сейчас его нет.
- **Маркетинг точки.** Домены, логотип, цвета, тексты, фото — в настройках
  tenant; site pages и media становятся tenant-scoped.
- **Панель владельца сети (суперадмин).** Список точек, сводные метрики,
  сравнение точек, управление тарифами платформы.
- **Панель точки.** Настройки сайта, цены, заказы, услуги, возвраты, письма,
  метрики — ровно то, что делается сейчас для одного store.

## Что уже готово и не придётся переделывать

- Почти все сущности tenant-scoped: users, projects, orders, payment_intents,
  testimonials, integrations, audit (`migrations/000003`, `000017`, `000015`,
  `000019`, `000014`, `000011`).
- Изоляция проверена тестами на уровне repository и агрегатов
  (`internal/infrastructure/database/analytics_repo_test.go:178-199`).
- Store-модуль (волна 0+) спроектирован tenant-scoped: настройки, прайс,
  страницы, медиа, события, письма — всё в tenant-скоупе, поэтому переход
  «один store → сеть» это смена способа выбора tenant, а не миграция данных.
- Роли/API-ключи/аудит дают готовую базу для «своих» прав точки.

## Что придётся решить, когда вернёмся к теме

1. **Идентификация tenant:** host → tenant; что делать с localhost и IP;
   нужен ли wildcard-домен.
2. **Роли:** точка/сеть; отдельная роль «владелец точки» с ограниченным
   доступом и аудитом.
3. **Домены и TLS:** per-tenant домены, сертификаты, редиректы.
4. **Изоляция данных:** общие материалы/цены сети против полной автономии точки.
5. **Биллинг платформы:** тариф за точку, лимиты, авто-выключение при
   неоплате (сейчас `status` есть только у пользователя).
6. **Правовые аспекты:** оферта/политика/реквизиты per-tenant (в витрине уже
   есть статические страницы — их надо сделать tenant-scoped).
7. **Миграция данных:** перенос текущего store в tenant «default» без
   простоя (или просто оставить default как первую точку).

## Порядок (когда вернёмся)

1. Миграция `store_settings`/`store_rates`/контента/медиа в tenant-скоуп
   (закладывается уже в волне store-admin).
2. Host→tenant resolution для публичных ручек + сайт по домену точки.
3. Роли и панель владельца точки.
4. Панель сети (сводные метрики, тарифы платформы).
5. Домены/TLS, биллинг, правовые страницы per-tenant.
