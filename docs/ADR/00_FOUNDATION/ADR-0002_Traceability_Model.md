# 1. Context

Stair Platform проектируется как долгоживущая инженерная система.

Каждый архитектурный элемент должен иметь возможность быть прослежен от возникновения бизнес-потребности до реализации и тестирования.

Без полной трассируемости невозможно:

- анализировать влияние изменений;
- гарантировать полноту реализации;
- автоматизировать проверку требований;
- проводить архитектурный аудит.

Необходимо определить единую модель Traceability.

---

# 2. Problem

При отсутствии единой модели возникает:

- потеря связи между требованиями и кодом;
- невозможность определить источник функциональности;
- отсутствие анализа влияния изменений;
- усложнение сопровождения проекта.

---

# 3. Decision

Во всей Stair Platform вводится обязательная модель сквозной трассируемости.

Каждый архитектурный артефакт обязан иметь связь как минимум:

- с источником возникновения;
- с собственной реализацией;
- с подтверждением реализации.

Разрыв цепочки трассируемости считается архитектурным дефектом.

---

# 4. Traceability Chain

Основная цепочка проекта

```

Business Goal
↓

Product Requirement
↓

Functional Requirement

↓

Architecture Decision

↓

Domain Model

↓

Engineering Model

↓

API

↓

Implementation

↓

Database

↓

Tests

↓

Release

```

---

# 5. Traceability Matrix

| Source | Target |
|---------|---------|
| Business Goal | Product Requirement |
| Product Requirement | FR |
| FR | ADR |
| ADR | Domain |
| Domain | Engineering |
| Engineering | API |
| API | Code |
| Code | Tests |
| Tests | Release |

---

# 6. Mandatory Links

Каждый FR обязан иметь:

- ADR;
- Domain;
- Tests.

Каждый ADR обязан иметь:

- причину создания;
- последствия;
- связанные требования.

Каждый API обязан иметь:

- FR;
- Implementation;
- Tests.

Каждая таблица БД обязана иметь связь с Domain Model.

---

# 7. Coverage Rules

Запрещается наличие:

- требований без реализации;
- реализации без требований;
- тестов без функциональности;
- API без документации;
- сущностей без Domain Model.

---

# 8. Traceability Report

Для каждого релиза автоматически формируется отчет.

Отчет содержит:

- процент покрытия требований;
- отсутствующие связи;
- неподтвержденные реализации;
- архитектурные нарушения.

---

# 9. Automation

Traceability должна автоматически проверяться средствами CI/CD.

Автоматические проверки включают:

- корректность ссылок;
- полноту связей;
- отсутствие разрывов;
- уникальность идентификаторов.

---

# 10. Consequences

Преимущества:

- полный анализ влияния;
- высокая сопровождаемость;
- прозрачность архитектуры;
- автоматизация документации;
- автоматизация аудита.

Недостатки:

- увеличение количества связей;
- необходимость поддержки реестра идентификаторов.

---

# 11. Alternatives Considered

## Частичная трассируемость

Отклонено.

Недостаточно для инженерной платформы.

---

## Только требования → код

Отклонено.

Не позволяет анализировать архитектуру.

---

## Без автоматизации

Отклонено.

Невозможно поддерживать крупный проект вручную.

---

# 12. Implementation

После принятия ADR:

- все документы используют идентификаторы;
- все API получают ссылки на FR;
- все тесты получают ссылки на требования;
- все изменения проходят Traceability Audit.
