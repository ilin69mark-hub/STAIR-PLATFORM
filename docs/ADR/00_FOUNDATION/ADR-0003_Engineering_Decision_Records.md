# 1. Context

Architecture Decision Records (ADR) предназначены для фиксации архитектурных решений.

Однако Stair Platform содержит большое количество инженерной логики, которая не относится непосредственно к архитектуре:

- математические модели;
- инженерные алгоритмы;
- расчетные формулы;
- геометрические зависимости;
- ограничения проектирования;
- производственные правила;
- стандарты расчета.

Изменение подобных решений существенно влияет на корректность работы платформы и требует отдельного механизма документирования.

---

# 2. Problem

Использование ADR для инженерных решений приводит к смешению архитектурных и инженерных вопросов.

В результате:

- усложняется навигация;
- снижается читаемость ADR;
- невозможно отделить архитектурную эволюцию от инженерной;
- затрудняется аудит математических изменений.

---

# 3. Decision

Вводится отдельный тип документа:

**Engineering Decision Record (EDR).**

EDR используется исключительно для фиксации инженерных решений.

ADR продолжает использоваться только для архитектурных решений.

---

# 4. Область применения EDR

EDR создается при изменении:

- инженерных алгоритмов;
- математических моделей;
- расчетных формул;
- Solver;
- Geometry Engine;
- Constraint Engine;
- Validation Engine;
- производственных правил;
- CAD-экспорта;
- CNC-экспорта.

---

# 5. Структура EDR

Каждый EDR содержит:

- идентификатор;
- название;
- статус;
- контекст;
- описание проблемы;
- принятое решение;
- инженерное обоснование;
- математическую модель;
- влияние на систему;
- связанные алгоритмы;
- связанные тесты;
- историю изменений.

---

# 6. Формат идентификатора

Используется формат:

```
EDR-0001
```

Примеры:

```
EDR-0007
EDR-0031
EDR-0152
```

---

# 7. Правила создания

EDR обязателен при:

- изменении инженерного алгоритма;
- изменении математической модели;
- изменении расчета нагрузки;
- изменении расчета геометрии;
- изменении производственных ограничений;
- изменении логики Solver.

---

# 8. Связь с ADR

ADR определяет архитектуру.

EDR определяет инженерную реализацию.

Пример:

```
ADR-0015
│
├── EDR-0008
├── EDR-0009
└── EDR-0012
```

---

# 9. Traceability

Каждый EDR обязан ссылаться на:

- ADR;
- FR;
- инженерный модуль;
- алгоритм;
- тесты.

---

# 10. Consequences

Преимущества:

- разделение архитектурных и инженерных решений;
- упрощение сопровождения;
- прозрачность изменений;
- аудит математических моделей;
- независимое развитие инженерного ядра.

Недостатки:

- увеличение количества документов;
- необходимость сопровождения EDR.

---

# 11. Alternatives Considered

## Использовать только ADR

Отклонено.

Причина:

архитектурные решения смешиваются с инженерными.

---

## Не документировать инженерные изменения

Отклонено.

Причина:

невозможно гарантировать воспроизводимость расчетов.

---

# 12. Implementation

После принятия ADR:

- создается каталог `EDR/`;
- вводится шаблон EDR;
- все инженерные изменения документируются через EDR;
- EDR включается в Traceability Model.
