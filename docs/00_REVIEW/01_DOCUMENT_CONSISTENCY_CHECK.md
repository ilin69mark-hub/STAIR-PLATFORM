# 1. Назначение

Настоящий документ определяет процесс проверки согласованности (Consistency Check) всей документации Stair Platform.

Цель проверки — гарантировать, что документы проекта не содержат противоречий, дублирования и нарушений архитектурных принципов.

---

# 2. Цель

Consistency Check обеспечивает:

- единое понимание архитектуры;
- отсутствие противоречий;
- отсутствие дублирования информации;
- целостность документации;
- корректные связи между документами.

---

# 3. Область проверки

Проверка распространяется на:

- Foundation;
- Product;
- Domain;
- Engine;
- Database;
- API;
- Application;
- AI;
- Manufacturing;
- Testing;
- Deployment;
- Release.

---

# 4. Проверяемые характеристики

Во время проверки анализируются:

- структура документации;
- терминология;
- требования;
- архитектурные принципы;
- инженерные принципы;
- зависимости;
- ссылки;
- идентификаторы;
- диаграммы;
- спецификации API;
- модели данных.

---

# 5. Типы проверок

## Terminology Check

Проверяется единообразие терминов.

Каждый термин должен иметь одно официальное определение.

---

## Requirement Check

Каждое требование должно:

- существовать;
- быть уникальным;
- иметь идентификатор;
- быть связано с документацией.

---

## Architecture Check

Проверяется соответствие:

- Architectural Principles;
- Engineering Principles;
- ADR;
- Standards.

---

## Dependency Check

Проверяются:

- входящие зависимости;
- исходящие зависимости;
- отсутствие циклических ссылок.

---

## Identifier Check

Проверяется уникальность:

- DOC;
- ADR;
- FR;
- NFR;
- CON;
- RISK;
- DEC;
- EDR (после внедрения).

---

## Cross Reference Check

Проверяются:

- внутренние ссылки;
- перекрестные ссылки;
- ссылки на диаграммы;
- ссылки на API;
- ссылки на UML;
- ссылки на ERD.

---

## Version Check

Проверяется:

- версия документа;
- совместимость версий;
- история изменений.

---

# 6. Проверка противоречий

Документация считается несогласованной, если обнаружены:

- различные определения одного термина;
- разные требования к одному компоненту;
- различные версии одной спецификации;
- конфликтующие архитектурные решения;
- конфликтующие инженерные ограничения;
- нарушение принципов проекта.

---

# 7. Проверка полноты

Каждый документ обязан содержать:

- назначение;
- цель;
- зависимости;
- Acceptance Criteria;
- историю изменений;
- утверждение.

---

# 8. Проверка связности

Для каждого документа проверяется:

- наличие входящих зависимостей;
- наличие исходящих зависимостей;
- наличие связанных требований;
- наличие связанных решений;
- наличие связанных диаграмм.

---

# 9. Результаты проверки

После завершения проверки формируется один из статусов.

## Passed

Замечаний нет.

---

## Passed with Notes

Обнаружены некритичные замечания.

---

## Failed

Обнаружены критические противоречия.

---

# 10. Отчет о проверке

Для каждого обнаруженного несоответствия фиксируются:

- идентификатор;
- описание;
- категория;
- критичность;
- затронутые документы;
- рекомендации по устранению.

---

# 11. Частота проведения

Проверка выполняется:

- после завершения каждого этапа Roadmap;
- перед утверждением Baseline;
- перед релизом;
- после крупных архитектурных изменений.
