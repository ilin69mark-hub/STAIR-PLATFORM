# 1. Назначение

Настоящий документ определяет правила анализа зависимостей (Dependency Analysis) для Stair Platform.

Dependency Analysis обеспечивает контроль архитектурных зависимостей между всеми компонентами системы и предотвращает нарушение архитектурных принципов.

---

# 2. Цель

Документ обеспечивает:

- контроль архитектурных зависимостей;
- предотвращение циклических зависимостей;
- снижение связанности модулей;
- повышение модульности;
- поддержку масштабируемости.

---

# 3. Основные принципы

Архитектура Stair Platform должна быть:

- ацикличной;
- модульной;
- расширяемой;
- независимой;
- предсказуемой.

Каждый модуль имеет четко определенную область ответственности.

---

# 4. Типы зависимостей

## Structural

Зависимости между архитектурными слоями.

---

## Logical

Зависимости бизнес-логики.

---

## Runtime

Зависимости во время выполнения.

---

## Data

Зависимости модели данных.

---

## API

Зависимости между контрактами.

---

## Build

Зависимости сборки.

---

## Documentation

Зависимости между документами.

---

# 5. Архитектурные уровни

```
Presentation
      │
      ▼
Application
      │
      ▼
Domain
      │
      ▼
Engineering
      │
      ▼
Infrastructure
```

Зависимости допускаются только сверху вниз.

Обратные зависимости запрещены.

---

# 6. Правила зависимостей

Каждый модуль может зависеть только от публичного контракта другого модуля.

Прямой доступ к внутренней реализации запрещен.

Все зависимости должны быть явно определены.

---

# 7. Запрещенные зависимости

Запрещается:

- циклическая зависимость;
- зависимость Presentation → Database;
- зависимость API → Database;
- зависимость Domain → UI;
- зависимость Solver → Web;
- зависимость Geometry → HTTP;
- зависимость AI → Database;
- зависимость Documentation → Source Code.

---

# 8. Анализ циклов

Перед утверждением архитектуры необходимо проверить отсутствие циклических зависимостей.

Любой обнаруженный цикл считается критическим дефектом.

---

# 9. Анализ связности

Для каждого модуля оцениваются:

- Coupling;
- Cohesion;
- Stability;
- Complexity;
- Fan-In;
- Fan-Out.

---

# 10. Матрица зависимостей

| Слой | Может зависеть от |
|------|-------------------|
| Presentation | Application |
| Application | Domain |
| Domain | Engineering |
| Engineering | Infrastructure |
| Infrastructure | Внешние сервисы |

Обратные зависимости запрещены.

---

# 11. Проверка изменений

При изменении любого модуля анализируется влияние на:

- архитектуру;
- API;
- модель данных;
- тесты;
- документацию;
- связанные ADR.

---

# 12. Отчет анализа

По итогам проверки формируется отчет, содержащий:

- карту зависимостей;
- найденные нарушения;
- циклические зависимости;
- рекомендации по устранению;
- оценку влияния изменений.

---

# 13. Автоматизация

Проверка зависимостей должна выполняться автоматически в CI/CD.

Обязательные проверки:

- отсутствие циклов;
- корректность импортов;
- соответствие слоям;
- отсутствие запрещенных зависимостей.
