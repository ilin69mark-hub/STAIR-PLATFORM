# 1. Назначение

Настоящий документ определяет правила проведения Traceability Audit для Stair Platform.

Traceability Audit проверяет полноту и корректность связей между требованиями, архитектурой, документацией, исходным кодом и тестированием.

Основная цель — гарантировать, что каждый элемент системы имеет подтвержденное происхождение, реализацию и проверку.

---

# 2. Цель

Traceability Audit обеспечивает:

- полную прослеживаемость требований;
- контроль реализации;
- контроль тестового покрытия;
- контроль архитектурных решений;
- анализ влияния изменений;
- упрощение сопровождения проекта.

---

# 3. Принципы трассируемости

Каждый артефакт проекта обязан иметь источник происхождения.

Каждый источник должен иметь реализацию.

Каждая реализация должна иметь подтверждение тестами.

Каждое изменение должно быть документировано.

---

# 4. Область проверки

Проверка распространяется на:

- Functional Requirements (FR);
- Non-Functional Requirements (NFR);
- Constraints (CON);
- ADR;
- Decision Log;
- Domain Model;
- UML;
- ERD;
- API;
- исходный код;
- тесты;
- релизы.

---

# 5. Цепочка трассируемости

Каждое требование должно прослеживаться по следующей цепочке:

```
Business Goal
      ↓
Product Requirement
      ↓
FR / NFR
      ↓
ADR
      ↓
Architecture
      ↓
Domain
      ↓
API
      ↓
Implementation
      ↓
Tests
      ↓
Release
```

---

# 6. Правила трассируемости

Каждый FR обязан иметь:

- архитектурную реализацию;
- связанный модуль;
- связанные тесты.

Каждый ADR обязан иметь:

- причину создания;
- область влияния;
- связанные требования.

Каждый API обязан иметь:

- источник требования;
- реализацию;
- тестовое покрытие.

Каждая сущность базы данных обязана быть связана с Domain Model.

---

# 7. Матрица трассируемости

Каждый элемент проекта должен быть связан минимум с одним элементом следующего уровня.

| Источник | Должен быть связан с |
|----------|----------------------|
| Business Goal | Product Requirement |
| Product Requirement | FR |
| FR | ADR / Domain |
| ADR | Module |
| Module | API / Database |
| API | Code |
| Code | Tests |
| Tests | Release |

---

# 8. Проверка покрытия

Проверяется отсутствие:

- нереализованных требований;
- неподтвержденных ADR;
- неиспользуемых модулей;
- неиспользуемых API;
- "мертвого" кода;
- тестов без требований;
- требований без тестов.

---

# 9. Анализ влияния

При изменении любого элемента определяется влияние на:

- требования;
- архитектуру;
- API;
- модель данных;
- тесты;
- документацию.

Результаты анализа фиксируются в Decision Log.

---

# 10. Отчет аудита

По итогам проверки формируется отчет, содержащий:

- количество проверенных связей;
- количество нарушений;
- перечень отсутствующих связей;
- перечень неподтвержденных требований;
- рекомендации по устранению.

---

# 11. Критерии успешного аудита

Аудит считается успешным, если:

- все требования имеют реализацию;
- все реализации имеют тесты;
- все тесты связаны с требованиями;
- отсутствуют разорванные цепочки трассируемости.

---

# 12. Периодичность

Traceability Audit проводится:

- после завершения каждого этапа Roadmap;
- перед фиксацией Baseline;
- перед выпуском релиза;
- после крупных архитектурных изменений.
