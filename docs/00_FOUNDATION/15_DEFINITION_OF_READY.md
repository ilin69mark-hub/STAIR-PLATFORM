# 1. Назначение

Настоящий документ определяет критерии готовности задачи к началу разработки (Definition of Ready, DoR).

Разработка не может быть начата до выполнения требований настоящего документа.

---

# 2. Цель

Definition of Ready обеспечивает:

- снижение количества ошибок;
- уменьшение числа доработок;
- повышение качества проектирования;
- прогнозируемость разработки;
- единый процесс начала работ.

---

# 3. Общие принципы

Любая задача должна быть:

- понятной;
- полной;
- проверяемой;
- согласованной;
- независимой;
- выполнимой.

Если хотя бы одно условие нарушено — задача считается неготовой.

---

# 4. Обязательные критерии готовности

Перед началом разработки должны существовать:

- описание задачи;
- цель задачи;
- область ответственности;
- критерии готовности;
- связи с другими задачами;
- необходимые документы.

---

# 5. Требования

Для каждой задачи должны быть определены:

- функциональные требования (FR);
- нефункциональные требования (NFR), если применимо;
- ограничения (CON), если применимо;
- связанные риски (RISK), если применимо.

---

# 6. Архитектурная готовность

До начала реализации должны существовать:

- утвержденная архитектура;
- необходимые UML-диаграммы;
- описание модулей;
- описание зависимостей;
- определенные интерфейсы взаимодействия.

Если изменение затрагивает архитектуру, соответствующий ADR должен иметь статус **Approved**.

---

# 7. Готовность данных

Если задача затрагивает хранение данных, должны быть подготовлены:

- ERD;
- описание сущностей;
- описание связей;
- описание ограничений;
- проект миграций.

---

# 8. Готовность API

Если задача включает API, должны быть подготовлены:

- спецификация OpenAPI;
- описание Endpoint;
- DTO;
- примеры Request;
- примеры Response;
- перечень кодов ошибок.

---

# 9. Готовность инженерных алгоритмов

Если задача относится к инженерному ядру, должны быть определены:

- математическая модель;
- инженерные правила;
- ограничения;
- алгоритм;
- входные параметры;
- выходные параметры;
- ожидаемый результат.

---

# 10. Готовность UI

Для задач пользовательского интерфейса должны существовать:

- описание пользовательского сценария;
- макет или прототип;
- требования к UX;
- требования к доступности.

---

# 11. Готовность тестирования

До начала разработки должны быть определены:

- стратегия тестирования;
- Acceptance Criteria;
- перечень Unit Tests;
- перечень Integration Tests;
- перечень Regression Tests (при необходимости).

---

# 12. Готовность документации

Все необходимые документы должны быть:

- созданы;
- согласованы;
- актуальны;
- иметь статус **Approved**.

---

# 13. Чек-лист Definition of Ready

Перед началом разработки необходимо подтвердить:

- [ ] задача описана;
- [ ] цель определена;
- [ ] область ответственности определена;
- [ ] FR готовы;
- [ ] NFR готовы;
- [ ] ограничения определены;
- [ ] архитектура утверждена;
- [ ] ADR утвержден (при необходимости);
- [ ] UML подготовлены;
- [ ] ERD подготовлена (при необходимости);
- [ ] API описан (при необходимости);
- [ ] Acceptance Criteria определены;
- [ ] тестовая стратегия подготовлена;
- [ ] документация утверждена.

---

# 14. Причины отказа

Задача считается неготовой, если:

- отсутствуют требования;
- отсутствуют критерии приемки;
- отсутствует архитектурное решение;
- отсутствуют необходимые диаграммы;
- отсутствует описание API;
- отсутствует описание модели данных;
- отсутствует описание инженерного алгоритма;
- отсутствует необходимый ADR.

---

# 15. Управление DoR

Definition of Ready пересматривается:

- при изменении процесса разработки;
- при изменении архитектуры;
- при изменении стандартов проекта.

Изменение настоящего документа допускается только посредством ADR.
