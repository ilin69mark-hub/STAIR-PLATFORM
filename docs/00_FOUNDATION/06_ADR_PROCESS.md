# 1. Назначение

Настоящий документ определяет единый процесс принятия архитектурных решений (Architecture Decision Record, ADR).

ADR является единственным допустимым механизмом изменения архитектуры Stair Platform.

Любое архитектурное изменение должно быть документировано.

---

# 2. Цель

Процесс ADR предназначен для:

- сохранения целостности архитектуры;
- фиксации причин принятия решений;
- предотвращения случайных изменений;
- обеспечения трассируемости развития проекта;
- сохранения инженерных знаний.

---

# 3. Что такое ADR

Architecture Decision Record — это документ, описывающий важное архитектурное решение.

ADR отвечает на вопросы:

- какая проблема существует;
- какие варианты рассматривались;
- почему выбран именно этот вариант;
- какие последствия он имеет;
- какие документы затрагиваются.

---

# 4. Когда ADR обязателен

ADR обязателен при:

- изменении архитектуры;
- изменении структуры проекта;
- изменении структуры STAIR-DOC;
- изменении API;
- изменении модели данных;
- изменении доменной модели;
- изменении инженерных алгоритмов;
- изменении принципов проекта;
- выборе новой технологии;
- отказе от существующей технологии;
- изменении форматов обмена данными;
- изменении правил безопасности.

---

# 5. Когда ADR не требуется

ADR не требуется для:

- исправления опечаток;
- улучшения формулировок;
- обновления примеров;
- добавления пояснений;
- исправления ошибок документации;
- реализации ранее утвержденной архитектуры;
- исправления дефектов без изменения поведения.

---

# 6. Жизненный цикл ADR

```
Proposal
    ↓
Analysis
    ↓
Alternatives
    ↓
Discussion
    ↓
Approval
    ↓
Implementation
    ↓
Verification
    ↓
Closed
```

Пропуск этапов запрещён.

---

# 7. Статусы ADR

Каждый ADR имеет один из следующих статусов:

- Draft
- Proposed
- Approved
- Rejected
- Superseded
- Deprecated

---

# 8. Правила утверждения

До утверждения ADR запрещается:

- изменение документации;
- изменение архитектуры;
- изменение структуры проекта;
- изменение API;
- изменение модели данных;
- изменение инженерных алгоритмов.

---

# 9. Правила реализации

После утверждения ADR обязательно обновляются:

- документация;
- диаграммы;
- требования;
- API;
- тесты;
- журнал изменений.

---

# 10. Структура ADR

Каждый ADR обязан содержать:

- номер;
- название;
- статус;
- дату;
- автора;
- контекст;
- проблему;
- варианты;
- выбранное решение;
- причины выбора;
- последствия;
- преимущества;
- недостатки;
- риски;
- план внедрения;
- связанные документы.

---

# 11. Формат идентификаторов

Нумерация ведётся последовательно.

Пример:

ADR-0001

ADR-0002

ADR-0003

...

Номера не переиспользуются.

---

# 12. Правила изменения ADR

Утвержденный ADR изменять запрещено.

При необходимости создаётся новый ADR.

Предыдущий ADR получает статус:

Superseded

или

Deprecated.

---

# 13. Связь ADR с документацией

Каждый ADR обязан содержать ссылки на документы STAIR-DOC.

Каждый документ STAIR-DOC обязан содержать ссылки на ADR, которые его изменяли.

---

# 14. Связь ADR с кодом

Каждый архитектурный модуль должен содержать ссылку на ADR, определивший его устройство.

Например:

ADR-0007

определяет структуру Geometry Engine.

---

# 15. Классификация ADR

Все ADR делятся на категории.

## Architecture

Изменение архитектуры.

---

## Engineering

Изменение инженерной модели.

---

## Domain

Изменение предметной области.

---

## API

Изменение контрактов.

---

## Database

Изменение модели хранения данных.

---

## Infrastructure

Изменение инфраструктуры.

---

## Security

Изменение модели безопасности.

---

## Performance

Изменение производительности.

---

## AI

Изменение AI-компонентов.

---

## Documentation

Изменение структуры документации.

---

# 16. Правила отклонения

ADR может быть отклонён если:

- нарушает архитектурные принципы;
- нарушает инженерные принципы;
- ухудшает сопровождаемость;
- создаёт технический долг;
- не имеет достаточного обоснования.
