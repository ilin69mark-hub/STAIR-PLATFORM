# 1. Назначение

Настоящий документ определяет единый процесс разработки Stair Platform.

Цель процесса разработки — обеспечить предсказуемое развитие проекта, исключить хаотичное изменение архитектуры, гарантировать качество инженерных решений и обеспечить полную трассируемость изменений.

Настоящий процесс обязателен для всех участников проекта.

---

# 2. Цели процесса

Процесс разработки должен обеспечивать:

- стабильность архитектуры;
- воспроизводимость разработки;
- инженерную корректность;
- высокое качество кода;
- минимизацию технического долга;
- прозрачность изменений;
- возможность долгосрочной поддержки проекта.

---

# 3. Основной жизненный цикл

Разработка любой новой функциональности проходит исключительно следующие этапы.

```
Идея
    ↓
Исследование
    ↓
Проектирование
    ↓
Документирование
    ↓
Архитектурное согласование
    ↓
ADR (при необходимости)
    ↓
Definition of Ready
    ↓
Разработка
    ↓
Code Review
    ↓
Тестирование
    ↓
Definition of Done
    ↓
Merge
    ↓
Release
```

Переход к следующему этапу без завершения предыдущего запрещён.

---

# 4. Этап 1. Исследование

На данном этапе определяется:

- проблема;
- цель;
- варианты решения;
- ограничения;
- риски;
- влияние на существующую архитектуру.

Результатом этапа является описание задачи.

---

# 5. Этап 2. Проектирование

Определяется:

- архитектура;
- предметная область;
- алгоритмы;
- зависимости;
- UML;
- API;
- модели данных.

При необходимости создаются новые документы STAIR-DOC.

---

# 6. Этап 3. Документирование

До начала реализации должны существовать:

- описание функциональности;
- Acceptance Criteria;
- входные данные;
- выходные данные;
- ограничения;
- ошибки;
- алгоритмы;
- примеры использования.

---

# 7. Этап 4. Архитектурное согласование

Проверяется:

- соответствие архитектуре;
- соответствие принципам проекта;
- влияние на остальные подсистемы;
- необходимость ADR.

---

# 8. Этап 5. Architecture Decision Record

Если изменение влияет на архитектуру, обязательно создаётся ADR.

Без утвержденного ADR изменение запрещено.

---

# 9. Этап 6. Definition of Ready

Перед началом реализации должны быть готовы:

- документация;
- архитектура;
- UML;
- Acceptance Criteria;
- тестовые сценарии;
- API;
- модели данных.

---

# 10. Этап 7. Разработка

Во время реализации запрещается:

- менять архитектуру;
- изменять бизнес-правила;
- изменять инженерные алгоритмы;
- менять API.

Подобные изменения допускаются только через возврат к этапу проектирования.

---

# 11. Этап 8. Code Review

Проверяется:

- соответствие документации;
- соответствие архитектуре;
- соответствие стандартам;
- читаемость;
- безопасность;
- производительность;
- тестируемость.

---

# 12. Этап 9. Тестирование

Минимальный набор тестов:

- Unit Tests;
- Integration Tests;
- Contract Tests;
- Regression Tests.

Для инженерных модулей дополнительно:

- Geometry Tests;
- Engineering Tests;
- Constraint Tests;
- Validation Tests.

---

# 13. Этап 10. Definition of Done

Функциональность считается завершённой только после выполнения всех требований Definition of Done.

---

# 14. Этап 11. Merge

Перед объединением обязательно проверяются:

- успешная сборка;
- успешное прохождение тестов;
- отсутствие конфликтов;
- обновление документации.

---

# 15. Этап 12. Release

Каждый релиз обязан содержать:

- версию;
- список изменений;
- миграции;
- обновление документации;
- журнал изменений.

---

# 16. Управление задачами

Каждая задача должна иметь:

- идентификатор;
- описание;
- цель;
- приоритет;
- зависимости;
- критерии готовности;
- ответственного;
- статус.

---

# 17. Управление изменениями

Любое изменение классифицируется как:

- Documentation;
- Feature;
- Bug Fix;
- Refactoring;
- Performance;
- Security;
- Architecture.

Архитектурные изменения требуют ADR.

---

# 18. Управление техническим долгом

Технический долг фиксируется отдельно.

Каждый элемент технического долга должен содержать:

- описание;
- причину;
- последствия;
- стоимость устранения;
- приоритет.

Запрещается скрытый технический долг.

---

# 19. Документирование реализации

После завершения реализации обязательно обновляются:

- STAIR-DOC;
- диаграммы;
- API;
- примеры;
- тестовые сценарии;
- журнал изменений.
