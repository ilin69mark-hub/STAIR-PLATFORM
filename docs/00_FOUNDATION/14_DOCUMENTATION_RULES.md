# 1. Назначение

Настоящий документ определяет правила создания, изменения, хранения и сопровождения документации Stair Platform.

Документация является единственным официальным источником информации о проекте.

Любая реализация должна соответствовать документации.

---

# 2. Цель

Документ обеспечивает:

- единообразие документации;
- актуальность информации;
- трассируемость изменений;
- воспроизводимость разработки;
- долгосрочную поддержку проекта.

---

# 3. Принципы документации

Документация строится на следующих принципах.

## Documentation First

Документ создается до начала реализации.

---

## Single Source of Truth

Каждый факт описывается только в одном месте.

Дублирование запрещено.

---

## Traceability

Каждое требование должно иметь возможность быть прослеженным:

Требование

↓

Документ

↓

ADR

↓

Код

↓

Тест

---

## Version Control

Каждый документ имеет собственную версию.

---

## Completeness

Каждый документ должен быть завершенным.

Не допускаются незавершенные разделы.

---

## Consistency

Документы не должны противоречить друг другу.

---

# 4. Структура документа

Каждый документ обязан содержать:

- название;
- идентификатор;
- версию;
- статус;
- автора;
- дату;
- назначение;
- зависимости;
- Acceptance Criteria;
- историю изменений;
- утверждение.

---

# 5. Статусы документов

Допустимые статусы:

- Draft;
- Review;
- Approved;
- Deprecated;
- Archived.

---

# 6. Правила создания

Новый документ создается только если:

- отсутствует аналогичный;
- существует самостоятельная область ответственности;
- документ не нарушает структуру STAIR-DOC.

---

# 7. Правила изменения

Изменения допускаются только после анализа влияния.

Если изменение затрагивает архитектуру, требуется ADR.

Все изменения должны отражаться в истории изменений.

---

# 8. Правила удаления

Удаление документов запрещено.

Документ переводится в статус:

Deprecated

или

Archived.

История должна сохраняться.

---

# 9. Правила именования

Имя документа:

```
NN_NAME.md
```

Примеры:

```
01_PRODUCT_VISION.md

03_ENGINE_ARCHITECTURE.md

12_API_SPECIFICATION.md
```

---

# 10. Правила ссылок

Каждый документ обязан содержать раздел Dependencies.

Указываются:

Входящие документы

Исходящие документы

---

# 11. Правила версионирования

Используется Semantic Versioning.

```
MAJOR.MINOR.PATCH
```

MAJOR

Несовместимые изменения.

MINOR

Расширение.

PATCH

Исправления.

---

# 12. История изменений

Каждый документ обязан вести журнал изменений.

Минимальная структура:

| Версия | Дата | Изменение |
|---------|------|-----------|

---

# 13. Управление качеством

Документация должна регулярно проверяться на:

- актуальность;
- полноту;
- непротиворечивость;
- соответствие архитектуре;
- соответствие стандартам.

---

# 14. Обязательные проверки

Перед утверждением документа проверяется:

- отсутствие конфликтов;
- корректность ссылок;
- наличие Acceptance Criteria;
- наличие Dependencies;
- корректность версионирования;
- наличие истории изменений.

---

# 15. Актуализация

Документация обновляется:

- после утверждения ADR;
- после изменения требований;
- после изменения архитектуры;
- после изменения API;
- после изменения модели данных;
- после изменения инженерных алгоритмов.

---

# 16. Ответственность

Ответственность за актуальность документа несет его владелец.

Архитектор отвечает за согласованность документации проекта.

---

# 17. Аудит

Документация подлежит обязательному аудиту:

- перед релизом;
- после архитектурных изменений;
- перед переходом к новой фазе Roadmap.
