# 1. Назначение

Настоящий документ определяет обязательные стандарты разработки Stair Platform.

Цель документа — обеспечить единообразие архитектуры, документации, программного кода, API, моделей данных и инженерных расчетов.

Все участники проекта обязаны соблюдать настоящие стандарты.

---

# 2. Область применения

Настоящий документ распространяется на:

- документацию;
- архитектуру;
- исходный код;
- API;
- базу данных;
- инженерные алгоритмы;
- AI-модули;
- тестирование;
- инфраструктуру;
- CI/CD.

---

# 3. Стандарты документации

Вся документация ведется исключительно в формате Markdown.

Каждый документ обязан содержать:

- название;
- идентификатор;
- версию;
- статус;
- автора;
- дату изменения;
- назначение;
- зависимости;
- Acceptance Criteria;
- историю изменений.

---

# 4. Стандарты именования документов

Документы именуются в формате:

```
NN_NAME.md
```

Пример:

```
03_ENGINE_ARCHITECTURE.md
```

Используются только:

- заглавные буквы;
- символ "_";
- расширение ".md".

---

# 5. Стандарты версионирования

Все документы используют Semantic Versioning.

Формат:

```
MAJOR.MINOR.PATCH
```

Пример:

```
1.0.0
```

Изменение:

MAJOR

при несовместимых изменениях.

MINOR

при расширении.

PATCH

при исправлениях.

---

# 6. Стандарты архитектуры

Архитектура обязана соответствовать:

- SOLID;
- Clean Architecture;
- Domain Driven Design;
- Modular Architecture;
- API First;
- Event Ready;
- ADR Driven.

---

# 7. Стандарты программного кода

Код обязан быть:

- читаемым;
- детерминированным;
- модульным;
- покрытым тестами;
- документированным.

Запрещается:

- дублирование;
- скрытая логика;
- магические числа;
- циклические зависимости.

---

# 8. Стандарты нейминга

Имена должны быть:

- однозначными;
- полными;
- предметно-ориентированными.

Запрещаются:

- tmp;
- data;
- object;
- helper;
- manager;
- util;
- misc;
- test1.

Исключения допускаются только при наличии общепринятого значения.

---

# 9. Стандарты API

Каждый публичный API обязан иметь:

- OpenAPI Specification;
- версионирование;
- описание ошибок;
- примеры запросов;
- примеры ответов;
- описание DTO.

---

# 10. Стандарты базы данных

Каждая таблица должна иметь:

- первичный ключ;
- ограничения;
- индексы;
- комментарии;
- миграции.

Все изменения схемы выполняются исключительно через миграции.

---

# 11. Стандарты UML

Все архитектурные диаграммы создаются в PlantUML.

Поддерживаемые типы диаграмм:

- Package Diagram;
- Component Diagram;
- Class Diagram;
- Sequence Diagram;
- Activity Diagram;
- State Diagram;
- Deployment Diagram.

---

# 12. Стандарты ERD

ER-диаграммы должны содержать:

- сущности;
- атрибуты;
- связи;
- ограничения;
- кардинальности.

---

# 13. Стандарты тестирования

Минимальный набор:

- Unit Tests;
- Integration Tests;
- Contract Tests.

Для инженерных модулей дополнительно:

- Geometry Tests;
- Validation Tests;
- Constraint Tests;
- Regression Tests.

---

# 14. Стандарты логирования

Каждое критическое действие должно логироваться.

Логи должны содержать:

- время;
- уровень;
- модуль;
- идентификатор операции;
- описание события.

Запрещается логировать:

- пароли;
- токены;
- секретные ключи;
- персональные данные без необходимости.

---

# 15. Стандарты обработки ошибок

Каждая ошибка должна иметь:

- уникальный код;
- уровень;
- описание;
- причину;
- рекомендации;
- возможность трассировки.

---

# 16. Стандарты безопасности

Обязательные требования:

- HTTPS;
- безопасное хранение секретов;
- RBAC;
- аудит;
- защита API;
- защита от распространенных веб-уязвимостей;
- журналирование действий пользователей.

---

# 17. Стандарты производительности

Система должна проектироваться с учетом:

- масштабируемости;
- кэширования;
- минимизации задержек;
- асинхронной обработки длительных операций.

---

# 18. Стандарты качества

Перед выпуском каждая функциональность обязана пройти:

- проверку архитектуры;
- Code Review;
- тестирование;
- проверку документации;
- проверку соответствия стандартам.

---

# 19. Управление стандартами

Изменение настоящего документа допускается исключительно посредством ADR.

Все изменения стандартов должны быть обратно совместимыми либо сопровождаться планом миграции.
