## B-1. Дневной LLM-бюджет не задан (🔴 открыт, требует человека)

Атака: ферма аккаунтов (регистрация открыта, 5/мин на IP, без верификации
email) × per-user лимит 200/мин → ночные расходы на OpenRouter.
Код-защита есть: `STAIR_AI_DAILY_LLM_BUDGET` (S-148) + метрика
`stair_assistant_llm_budget_denied_total`; **дефолт = выключено**.

- Действие: задать `STAIR_AI_DAILY_LLM_BUDGET` (например 2000) в Helm/ENV API.
- Действие: алерт Prometheus на `rate(stair_assistant_llm_budget_denied_total[5m]) > 0`.
- Снять: когда env задан + алерт в правилах, отметить B-1 DONE.

## B-2. Верификация email при регистрации (🟡 требует человека/инфра)

Проблема: `POST /api/v1/auth/register` создаёт аккаунт без подтверждения →
мультиаккаунтный обход любых per-user лимитов (B-1 смягчает, но не закрывает).
Нужен SMTP-провайдер (ключ) + токены подтверждения + UI «подтвердите почту».

- Действие: выбрать SMTP (Resend/Mailgun/Amazon SES) → задать ключ (реестр
  исключений, новая запись E12) → реализовать flow.
- Без этого per-user лимиты обходятся фермой аккаунтов.

## B-3. Live-LLM safety-eval (🟡 требует staging/ключа)

Слепая зона S-148: eval ловит отражение атак в ответе, но не проверяет
поведение живой модели при отравленной истории/RAG (сценарий «системный промпт»).

- Действие: staging с реальным OpenRouter + прогон `eval-safety.jsonl` с живым
  бэкендом; эталон ответов (ручная проверка на утечку system prompt/PII).
- Снять: когда eval с живой моделью зелёный и внесён в регламент.

## B-4. Прод-конфигурация безопасности (🔴 открыт, требует человека)

Из `docs/SECURITY_EXCEPTIONS.yml` (E01–E11) — всё ждёт человека: ключи, UFW,
TLS/certbot, HSTS, GPG-бэкапы, TG-алерты, NP staging→прод.
Прод без любого из пунктов запускать нельзя (`prod_gate` в реестре).

## B-5. Аутсорс-лимиты: IP/ротация (🟡 требует инфра)

Per-IP лимиты (login 10/мин, register 5/мин) обходятся через NAT/прокси.
`STAIR_TRUSTED_PROXIES` настроен (S-120) — нужно подтвердить, что реальные
клиенты приходят через доверенный прокси, иначе ферма с одного IP продолжит
работать.
