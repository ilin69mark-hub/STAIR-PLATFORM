# Changelog

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
проект следует [Semantic Versioning](https://semver.org/lang/ru/).

## 2026-10-03 — Передача владения проектом

Проект можно передать другому участнику одной кнопкой в блоке «Участники
проекта». Передача меняет владение в двух местах сразу (запись владельца среди
участников и `projects.owner_id`) одной транзакцией: прежний владелец становится
редактором, новый — владельцем, а прежний может уйти из проекта сам. Передать
может владелец проекта или любой участник с платформенным правом
`staff.project_transfer` (есть только у владельца компании), но только тому, кто
уже участник проекта.

Заодно список участников показывает имя и почту вместо идентификаторов: выбрать
«кому передать» по UUID было невозможно. В журнале аудита появляется
`project.transferred`.

## 2026-10-03 — Удаление сотрудника с передачей проектов

В плитке «Команда» появилась кнопка «Удалить»: сначала сервер считает и
показывает точные цифры (сколько проектов перейдёт другому человеку, сколько
расчётов, комментариев и заказов останется в истории), затем требуется выбрать
получателя проектов — без выбора удаление нельзя подтвердить. Проекты
переезжают в одной транзакции вместе с записью владельца в участниках
проекта; сотрудник удаляется мягко (строка остаётся, вход закрыт, история
цела), действие попадает в журнал аудита как `user.deleted`.

Новые ручки: `GET /api/v1/admin/users/{id}/deletion-preview` и
`DELETE /api/v1/admin/users/{id}?transfer_to=<uuid>`, право `staff.delete`
(действие). Запрещено удалять себя, последнего владельца компании; владельца
может удалить только владелец; получателем может быть только активный
сотрудник того же тенанта. Попутно закрыта дыра: удалённый сотрудник мог войти
в систему, потому что поиск по почте не смотрел на `deleted_at`.

Добавлен `scripts/cleanup-dev-users.sh` — уборка тестовых сотрудников и их
проектов в dev-окружении (по умолчанию пробный прогон, удаление только с
`--apply`).

## 2026-10-02 — Кабинет: приветственный экран с плитками вместо вкладок

Верхний уровень кабинета переделан: вместо вкладок «Проекты / Администрирование
/ Аудит / Магазин» — плитки по блокам бизнеса («Проекты», «Сайт и витрина»,
«Цены и расчёт», «Продажи и деньги», «Производство», «Реклама и трафик»,
«Команда»). Плитка появляется, только если у человека есть хотя бы одна метрика
внутри неё; разделы открываются по своим метрикам и идут одним скроллом.
Журнал аудита переехал внутрь «Команды», ставки расчёта — внутрь «Цены и
расчёт» (у них появилась своя группа настроек и своё право `price.rates`),
«Отзывы» — внутрь «Сайта и витрины», заказы — внутрь «Продажи и деньги».
Кнопка выхода доступна на любом экране: раньше её не было ни в админке, ни в
аудите, ни в магазине.

Убраны метрики `project.view` и `project.edit` (доступ к проекту даёт членство в
проекте), реестр — 34 метрики; `production.report` убрана из роли `sales`.


## [Unreleased]

### Added

- **Store Admin wave 0**: отдельная панель настроек текущего store с авторизацией, контактами, SEO, счётчиками, параметрами расчёта, прайсом материалов, каталогами материалов/услуг и заказами; Docker Compose, Makefile, CI/CD и image build для `store-admin`.
- **Точечные выдачи прав сотрудникам** (EDR-0041): владелец выдаёт
  сотруднику конкретные метрики построчно, у каждой — уровень «видеть» /
  «менять», а у действий (возврат платежа, выгрузка, выдача ключа) один
  переключатель. Роль стала шаблоном прав по умолчанию. Реестр — 36
  метрик в восьми блоках.
- Новые роли: `owner` (владелец) и `sales` (руководитель отдела продаж).
- `GET` и `PUT /api/v1/admin/users/{id}/grants` — чтение и замена набора
  прав. Каждая выдача и каждый отказ попадают в журнал аудита.
- Настройки витрины делятся на группы: `PUT /api/v1/admin/store/settings/{group}`,
  где группа — contacts, company, social, seo или rates. У группы своё
  право, поэтому «SEO» и «реквизиты» выдаются отдельно.
- Мягкое удаление сотрудника (`users.deleted_at`).

### Changed

- **Единый кабинет**: админ-панель и панель магазина объединены в одно
  приложение `frontend`. Отдельные `frontend-store-admin`, образ
  `store-admin`, порт 5177 и их джобы CI удалены.
- **Разделы магазина** (цены, настройки витрины, материалы, услуги, заказы,
  платежи) перенесены во вкладку «Магазин»; экран заказов остался один —
  табличный из админки, дубль из панели магазина удалён.
- **Доступ по правам вместо роли**: вкладки и разделы кабинета отбираются по
  `User.permissions` (новое поле в ответе `/auth/me`), а не по `role === 'admin'`.
  Раздел виден по `*.list`, кнопка мутации (смена статуса заказа, возврат
  платежа) требует `*.manage`.
- **Загрузчики данных**: три похожих хука (`useLoad`, `useLoadRethrow`,
  `useAsync`) схлопнуты в один `frontend/src/lib/useLoad.ts` с защитой от
  гонки и ручным `reload`.
- **Права проверяются по метрике и уровню, а не по роли.** Раньше роль
  `admin` давала всё сразу, а интерфейс показывал кнопку изменения по
  праву на чтение — запись отбивалась 403. Теперь кнопка появляется при
  своём уровне, а раздел — при наличии метрики.
- Скоупы API-ключей — те же имена метрик, что и в интерфейсе.
- Ответ сессии содержит `grants` (метрика + уровень); `permissions`
  оставлены для совместимости с текущим клиентом.

## [0.2.0] — 2026-09-18

### Added

- **Живая валидация при вводе** (S-P5): иделомоментные (validation-only)
  эндпоинты `POST /api/v1/public/stairs:validate` (анонимный) и
  `POST /api/v1/stairs:validate` (авторизованный) — возвращают `{validation}`
  без геометрии/цены/версий (rate-limit `STAIR_VALIDATE_RATE_LIMIT`, по
  умолчанию 120/мин). В конструкторе КВ и редакторе проекта — debounce 700 мс:
  баннер блокировок с guide/fix, подсветка проблемных полей, кнопки
  «Применить» (вариант советника/вариация), нагрузка в logAction
  `stair.live_suggestion_applied` / `stair.live_variation_applied`; общий
  модуль `@shared/liveValidate` (нормализация ответов, configKey-дедупликация
  запросов, cancel/invalidate).
- **Observability-стек** (P3, EDR-0021): Prometheus + Alertmanager + Grafana +
  Jaeger через оверрайд `deployments/observability/docker-compose.observability.yml`;
  13 alert-правил по реальным метрикам `/metrics` (availability 99.9%,
  latency p95/p99, engine calc/optimize, БД-пул, circuit breaker, memory,
  rate-limit); дашборд Grafana «STAIR — API Golden Signals» с автопровижном
  datasource; `make obs-up / obs-tracing-up / obs-down / obs-config`.
- **Worker в dev-стеке** (P3, EDR-0020/0035/0018): сервис `worker` в
  `deployments/docker-compose.yml` (тот же образ, `/bin/worker`) потребляет
  общую Redis-очередь — async-расчёты `calc.calculate`, доставка webhook,
  очистка истёкших сессий/sso_states и аудит-ретенция; env
  `STAIR_CLEANUP_INTERVAL`/`STAIR_AUDIT_RETENTION_DAYS`/`STAIR_WORKER_SHUTDOWN_TIMEOUT`.
  API в compose получил `STAIR_REDIS_ADDR=redis:6379` — постановка заданий в
  общую очередь (иначе API enqueue-ил в in-memory и воркер не видел джобы).
- **Трейсинг worker** (P3): `cmd/worker` инициализирует OpenTelemetry (OTLP,
  Jaeger-сервис `stair-platform-worker`); каждый обработанный job — span
  `job.process` с атрибутами job.id/type/attempts и error при провале,
  включается в обсервабилити-оверрайде через STAIR_TRACING_ENABLED.
- **Release versioning**: пакет `internal/version` (Version/Commit/BuildTime)
  заполняется через ldflags во всех артефактах (Makefile `build-api`,
  Dockerfile API, CI build-push-action); версия логируется на старте API/worker;
  `make version` печатает текущую версию.
- **Perf baseline** (P2): `make bench` — бенчмарки Calculate/Generate/Optimize,
  базовая линия в `benchmarks/baseline.txt`.
- **Backup/recovery PostgreSQL** (P2): `make backup / restore / backup-check`
  — `pg_dump -Fc` + sha256 + метаданные, восстановление в отдельную БД со
  сверкой checksum, round-trip проверка обратимости.
- **Secret scan** (P3): Gitleaks в CI (`security-scan`, вся история, v8.30.1);
  конфиг `.gitleaks.toml` с allowlist'ом для публичного AWS SigV4 test-vector
  и Stripe test-ключей в unit-тестах. Проверка 117 коммитов — 0 утечек.

### Changed

- **Понятные тексты валидации** (S-P6): каждая issue несёт `Param`/`Guide`/
  `Fix` на русском прямо из `Validate` (шаблон правила рендерится через
  `validation.RenderGuide`) — без прохождения через advisor, поэтому готовые
  подсказки попадают в сохранённые снапшоты. Общий словарь
  `@shared/validationText` (severity→«Ошибка/Предупреждение», element→
  «Помещение/Просвет/Ступень/…»); таблица нарушений в админке без технической
  колонки «Код», Severity/Элемент переводятся, фолбэки вместо «—».
- **Варианты при невписываемости в помещение** (S-P6): движок
  `forRoomFitTol` перебирает допуск `fitEps`→`fitTol=50 мм` и собирает до двух
  вариантов каждого типа: A «сделать круче», B «заменить марш» (L/U), C другие
  типы (до 2: ближайший + самый компактный), D «сделать марш уже / спираль
  компактнее» (тот же тип). Спиральные кандидаты получают согласованные
  параметры марша через `SpiralResult.Apply` (проступь=WalkTread, угол) —
  больше не отбрасываются как «проступь вне нормы» на ноль-конфигурациях.
  Варианты снабжены суммаркой (габариты, число ступеней, угол, «впритык к
  помещению (запас < 50 мм)»).
- CI: сборка API-образа передаёт VERSION/COMMIT/BUILD_TIME в образ.
- CI: actions подняты на актуальные major (Node 24-рантайм): checkout v7,
  setup-go v7, setup-node v7, upload-artifact v7, docker/setup-buildx-action
  v4.4.1, docker/login-action v4.6.0, docker/build-push-action v7.4.0.
- `report-400.spec.ts`: комментарий о валидном радиусе спирали приведён к
  документированному окну [900,1200] (`boundary.spec.ts`); узкое окно ~960 —
  частный случай (явный шаг 165–172, H 2680–2720).
